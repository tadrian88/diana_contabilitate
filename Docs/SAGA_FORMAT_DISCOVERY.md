# SAGA Format Discovery

Status: verified file format; local handoff and acknowledgement remain unresolved.

## Source of truth

- SAGA version/product: current SAGA C manual as available on 2026-09-14. The
  import contract has no separately published schema version or XSD.
- Primary source: [SAGA C — Import date](https://manual.sagasoft.ro/sagac/topic-76-import-date.html).
- Corroborating accepted-shape evidence: SAGA's official forum contains a 2026
  invoice import example using UTF-8 XML, `dd.mm.yyyy` dates, dot decimal
  separators and the documented hierarchy. Its reported routing problem was an
  old company fiscal code, confirming that `ClientCIF`/`FurnizorCIF` determine
  Intrări versus Ieșiri.
- Diana policy identifier: `SAGA_C_INVOICE_XML_2026_V1`. This versions Diana's
  mapping, not a version claim made by SAGA Software.

## Verified import contract

SAGA C imports unarchived XML files selected by the user in **Diverse > Import
date**. Invoice files use the deterministic naming shape
`F_<cod-fiscal>_<numar-factura>_<data-factura>.xml` and the hierarchy:

`Facturi > Factura > Antet` plus `Detalii > Continut > Linie`.

For received supplier invoices, Diana writes the supplier to `Furnizor*` and
the accounting client to `Client*`. SAGA routes the file to **Intrări** when
the configured company's fiscal code equals `ClientCIF`. Imported entries are
not automatically validated; the user performs import/validation in SAGA.

The implemented subset is UTF-8 XML and uses:

- header: supplier name/CIF, client name/CIF, invoice number, invoice date,
  optional due date, and non-RON currency;
- line: sequence, description, optional information, unit, quantity, unit
  price, net value, VAT percentage/value, account, and optional deduction code;
- `FacturaID`: the immutable Diana invoice ID;
- date text: `dd.mm.yyyy`;
- decimal text: exact base-10 values with `.` and no locale/group separators.

No undocumented summary, VAT account, exchange rate, item, warehouse, document
type, SPV index or payment tag is emitted.

## Classification contract

The exporter consumes persisted final decisions; it never runs rules.

| Dimension | Accepted external value | SAGA output |
|---|---|---|
| ACCOUNT | explicit account code such as `628.01` | `Cont` |
| VAT | exact numeric rate equal to the source line rate | source `ProcTVA` |
| DEDUCTIBILITY | `N50` | `TipDeducere=N50` (documented 50% limitation) |
| DEDUCTIBILITY | `I` | `TipDeducere=I` (documented fully non-deductible) |
| DEDUCTIBILITY | `SAGA_DEFAULT` | optional tag omitted; this is a technical adapter instruction, not inferred tax advice |

Pending, missing, textual/demo, inconsistent or unknown values are permanent
data errors. No account or tax default is invented.

## Document and currency support

- `Invoice`: supported.
- `CreditNote`: explicitly rejected. SAGA documents interactive storno behavior
  but does not document how a UBL CreditNote maps into this invoice-import XML.
- RON: supported; optional `FacturaMoneda` omitted.
- non-RON: supported as the documented `FacturaMoneda` value. The import
  contract exposes no exchange-rate field, so Diana neither looks up nor invents
  a rate.

## Handoff and acknowledgement

The verified mechanism is local/manual file selection by a SAGA desktop user.
No cloud API, watched-folder protocol, provider idempotency key, callback or
machine-readable import acknowledgement is documented. Therefore:

- generating/storing the file proves only `GENERATED`;
- it does not prove delivery, SAGA acceptance, validation or accounting entry;
- Diana must not transition to `EXPORTED` from file generation alone;
- repeated generation is protected only by Diana's invoice revision/exporter
  version uniqueness. SAGA-side duplicate prevention depends on the user's
  chosen synchronization field (for example number + date), not exactly-once
  delivery.

## Unresolved verification

- Credit-note/storno mapping is not verified.

- Full authentication/RBAC is not implemented, so accounting artifacts must not

## Accounting Domain V2 derivation — supersedes the legacy classification contract for V2 only

The table above remains LEGACY_V1 behavior and preserves historical artifacts. Its DEDUCTIBILITY values are vendor import instructions; N50/I/SAGA_DEFAULT are not universal VAT/expense domain enums. The four independent V2 decisions are ACCOUNT, VAT_TREATMENT, VAT_DEDUCTIBILITY and EXPENSE_TAX_TREATMENT.

V2 generator calls the shared authoritative readiness validator and rechecks automatic predicates before serialization. Only an explicitly accountant-approved mapping of ORDINARY / IMMEDIATE, FULL VAT deduction and FULLY_DEDUCTIBLE expense permits TipDeducere omission. Source VAT rate/category/amount remain source facts. FULL VAT with NONDEDUCTIBLE expense and all other limited/special/period/inapplicable combinations are not representable by the initial mapping and remain grouped CLASSIFICATION review; no N50/I inference is added.

Mapping policy/version/approval and model/profile/pack/rule/source evidence are retained in immutable invoice and artifact snapshots. V2 exporter uses SAGA_C_DOMAIN_V2_V1/<mapping version>; legacy exporter version and XML bytes are unchanged. Real production mapping approval/desktop SAGA acceptance is still outstanding. Synthetic opt-in XML is engineering evidence only and is rejected by the production generator. Generation/download still does not imply EXPORTED.
